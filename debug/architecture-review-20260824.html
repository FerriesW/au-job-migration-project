Verdict

Not spaghetti. Phase 1 was coherent and stayed coherent. What had drifted was narrower and more dangerous than mess: code the documentation claimed was alive but was not, and a headline claim with no reproducible evidence behind it. Both are fixed. The scattered feeling came from decisions being surfaced one at a time instead of being absorbed by the records that already existed.

1 · One interface over three query engines

Strong · applied

Files

adzuna_pipeline/engines.py · adzuna_pipeline/equivalence.py · scripts/compare_engines.py · scripts/apply_athena_ddl.py

Problem

The project's central claim — BigQuery, Athena and Snowflake agree over the same data — was checked with throwaway scripts in a temp directory. The numbers reached three READMEs; the scripts did not survive. Meanwhile the Athena submit-poll-fetch cycle had been written twice inside a single file. There was no module for "ask a warehouse a question", so every caller re-derived one, and none of them left anything behind.

Solution

A QueryEngine interface of three things — a name, run, close — with three adapters behind it. Every value comes back normalised to a string, which is the part that actually earns the module: without it, "do the engines agree?" degenerates into arguing about 4704 vs '4704' vs Decimal('4704'). The questions themselves became data in equivalence.py, each spelled three ways side by side.

Before — no module

scratchpad/equiv.py — own client, own polling
scratchpad/three_way.py — own client, own polling
apply_athena_ddl._run — polling, copy 1
apply_athena_ddl._fetch_rows — polling, copy 2

Four implementations. Two deleted themselves. Evidence: none.

After — a real seam

interface: name · run(sql) · close()
credentials for three clouds
submit / poll / fetch, header stripping
Decimal, date, bool → comparable strings
scanned-bytes reporting where it exists
BigQuery
Athena
Snowflake

Benefits

  • Leverage: two callers already. apply_athena_ddl.py lost 100 lines by handing polling to the module.
  • Locality: a fourth engine, or a change to how results are compared, is one file.
  • The interface is the test surface: normalise() is pure and testable without a cloud; everything needing credentials sits behind run.
  • Three adapters, not one — this seam is real, not hypothetical.

Result, run for real: all five checks agree across three engines. It also produced the cost comparison ADR-0002 promised — BigQuery scanned 618,900 bytes for the same five questions, Athena 3,171,347. A 5× gap that is storage format, not workload: BigQuery reads named columns, Athena decompresses whole JSON objects.

2 · Configuration read in exactly one place

Strong · applied

Files

adzuna_pipeline/config.py · extraction/client.py · extraction/judge.py · tests/test_env_example_documents_settings.py

Problem

config.py looked like the single seam for configuration, but two modules went around it with os.getenv. Meanwhile a RuntimeSettings class and two documented variables had no callers at all. The existing test only checked that declared settings were documented — never the reverse — so dead configuration passed cleanly.

Before

.env  ──┬─→ config.py (settings classes)
        ├─→ client.py   os.getenv("DASHSCOPE_BASE_URL")
        └─→ judge.py    os.getenv("JUDGE_MODEL")

RuntimeSettings ──→ (nobody)
LOG_LEVEL, SAMPLE_LIMIT documented, unread

After

.env  ──→ config.py ──┬─→ client.py
                      ├─→ judge.py
                      └─→ engines.py

test asserts BOTH directions:
  declared ⊆ documented
  documented ⊆ declared ∪ {boto3's two}

Benefits

Locality: one module reads the environment, so "what does this project need configured?" has one answer. The bidirectional test makes that structural rather than aspirational — it is what surfaced the two dead variables, and it will surface the next one.

3 · Deleting what the documentation claimed was alive

Strong · applied

Problem

ADR-0002 stated that sync_bq_to_snowflake.py was "repurposed rather than discarded". It was neither: loading from an external stage turned out to be four SQL statements, and the 230-line script was never touched again. Three other documents described the architecture that ADR-0002 had rejected.

Applying the deletion test

Deleting the script concentrates nothing and moves nothing — the behaviour already lives in snowflake/03–04. That is the signature of a module that stopped earning its keep, and the only thing keeping it was a sentence in a record.

  • scripts/sync_bq_to_snowflake.py — deleted, with its console-script entry
  • RuntimeSettings and get_runtime — deleted
  • docs/snowflake-setup-guide.md, HANDOFF.md — deleted; both described the rejected portability architecture
  • ADR-0002's prediction left visible and corrected in place, not quietly edited out
  • dev_log.txt — v0.11.0 covers the two months of Phase 2 it had missed

4 · Shared entry-point plumbing

Worth doing · applied

Six copies of _configure_logging and nine of the project-root boilerplate, already drifting apart in which loggers they silenced — which matters here, because httpx at INFO writes the Adzuna application key into stdout. Now one module.

Honestly shallow: the interface is nearly as large as the implementation. It earns its place on locality alone — a new noisy dependency is one line, in one file, instead of six edits someone will do five of.

What is still open

Separating the Snowflake dbt models decided, not yet built

One dbt project, two targets: Snowflake models would run against BigQuery unless isolated. Resolved as +enabled driven by target type, set once in dbt_project.yml per path — dbt's standard idiom, one project, one CI.

⚠ ADR-0002 says "no target.type branching anywhere". That was written against branching inside a model's SQL for portability; selecting which models exist per warehouse is a different thing. The record needs one sentence drawing that line — otherwise the next reader is right to object.

The gate cannot check the multi-cloud claim

compare_engines.py needs credentials for three clouds, so ADR-0001's hermetic pull-request gate can never run it. Structural, not fixable: it is a release check. Worth naming so nobody assumes CI is watching.

The landing-zone uploaders are already fine

GcsRawUploader / S3RawUploader behind RawUploader, with the key derived from the payload so neither adapter can choose where its object lands. Two adapters, real seam, no change needed. Noted so a future review does not re-suggest it.

Top recommendation

Build the Snowflake dbt layer next, and amend ADR-0002's one sentence first. Everything else in the cleanup is done; that is the single decision left blocking forward motion, and it is blocked only by wording in a record I wrote.

Scope it as one vertical slice — two staging models off the VARIANT tables plus the one mart that needs lateral flatten. Replicating the ANZSCO marts would mean loading four seeds into Snowflake to demonstrate nothing Snowflake-specific.

With 24 days of trial left, the constraint is the clock, not the code.
